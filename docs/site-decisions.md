## 2. 技术栈 ✅ Astro 7

**版本事实（已核实）**：稳定大版本 7.x，最新 `astro@7.3.5`，要求 Node ≥ 22.12.0。

选它的理由，按权重：

1. 冻结契约里的 6 条 frontmatter 校验规则，在 Astro 里就是一个 zod schema（约 20 行）；在 Eleventy 里是一套要自己维护的脚本。
2. `glob({ base: './content' })` 是官方支持的选项 —— 契约要求「`content/` 放仓库根」，这条直接成立，不需要 hack。
3. 图片与正文同目录 + 构建期优化是原生能力（`<Picture>` 出多格式 srcset），不引额外插件。
4. C 方向（高对比编辑风）要精细的版面控制，组件化比模板拼接更扛得住后续改动。

**已核实的代价（不是听来的，是我查到的）**：

- Astro 7 把 Markdown 处理器换成了 Rust 的 Sätteri，**recma 插件不再支持**。→ 我的对策：TOC 自研（解析 headings），不依赖 remark/rehype 生态。
- `sharp` 是 optionalDependency 且为 native 二进制；包管理器严格模式下可能要显式安装。
- Astro 本体直接依赖 53 个 vs Eleventy 的 33 个。**这只影响构建机，不影响产出物** —— 两边产物都是纯静态 HTML，这也是我没把依赖数当决定因素的原因。

### 依赖预算

| 包 | 状态 | 理由 |
|---|---|---|
| `astro` | 必须 | 框架本体 |
| `sharp` | 必须 | 图片优化（Astro 的默认图片服务） |
| `@astrojs/rss` | 计划加 | 你选了要 RSS。官方包，非零配置（要写一个 `rss.xml.js` 端点） |
| `@astrojs/sitemap` | **待你同意** | SEO 用。不是必须 —— 但站点要能被搜索引擎收录，这个包比手写 sitemap 划算 |
| `@astrojs/mdx` | **不加** | 你选了纯 Markdown |
| 其它 | 一律自研 | TOC、代码复制按钮、阅读时长、标签页、归档页、404 —— 都是几十行的活，不值得引包 |

## 3. 部署 ✅ Cloudflare Pages（先用免费 `*.pages.dev` 子域）

**你的前提**：无域名、无 ICP 备案、读者以中国大陆为主。

**我没有根据地能给你的承诺**：大陆访问速度这块，除了 Vercel（官方自己承认可能缓慢或失败），Cloudflare Pages 和 GitHub Pages 我**只有第三方经验帖，没有官方数据**。所以下面是路线选择，不是性能承诺。

选择 Cloudflare Pages 的理由：¥0、零运维、不需要备案；产出是纯静态 HTML，**托管商不锁死** —— 以后想搬到国内云或 VPS，成本是"改 DNS + 传文件"。

**已知代价**：大陆访问可能不稳定。等你决定买域名（约 ¥50/年）后，把自定义域绑上去通常比 `pages.dev` 子域略好，但**同样不保证**。真要把大陆速度当硬指标，唯一的路是域名 + ICP 备案 + 国内云，约 2–4 周流程。

> **推送到 GitHub 时踩到的环境事实**（下次会再遇到）：这台机器的 `hosts` 里有 27 条 GitHub 域名指向 `127.0.0.1`，
> 由 **`Steam++.Accelerator`（Watt Toolkit）** 在 443/80 上反向代理 —— 那是加速工具，不是屏蔽。
> 所以 `github.com` 能连上（经它转发），推送失败的真实原因只可能是**凭据**。
> 排查时**不要**用 `GIT_TERMINAL_PROMPT=0` / `GCM_INTERACTIVE=never`，那会把「缺凭据」伪装成「推不上去」。
>
> **另一个坑**：`curl` / `Invoke-WebRequest` 走 github.com 时可能返回 `HTTP 000`（加速器的 HTTP 转发路径会抽风），
> **而同一时刻 `git ls-remote` 却是通的**。所以判断仓库可见性不要用 HTTP 请求，用下面那条命令。

### 仓库可见性：已转私有（2026-09-25）

站主决定把仓库转为私有。原因是：**草稿的保密性等于仓库的保密性** ——
`draft: true` 的文章不会发布到网站，但它的 `.md` 原文就在仓库里；
仓库公开时，任何人翻仓库都能读到未发布的草稿。

**怎么验证它确实是私有的**（不依赖 HTTP，绕开加速器抽风）：

```powershell
git ls-remote --heads origin                                              # 带凭据：应当成功
git -c credential.helper= ls-remote --heads https://github.com/NorthenCedar/personal.git
```

实测（2026-09-25）：第一条成功读到 `refs/heads/main`；第二条报
`fatal: could not read Username for 'https://github.com'` ——
**服务器拒绝匿名访问，确认为私有。**

### 变更记录：评论从「不做」改为「自建」（2026-09-26）

**为什么改**：站主提出想要评论功能。

**为什么是自建而不是现成方案**（这是这次变更的核心判断）：

| 方案 | 为什么没选 |
|---|---|
| Giscus / utterances | 依赖 GitHub Discussions 加载 —— 大陆读者不稳；**读者必须有 GitHub 账号才能留言**，门槛过高；且是 iframe，**样式无法与站点设计语言一致**（站主的明确要求） |
| Waline / Twikoo | 要自己长期维护一个后端 + 数据库，且多在境外 |
| **自建 Functions + D1** | ✅ 同域名、无第三方、**样式完全可控**、数据在自己的 Cloudflare 账号里 |

**代价（写清楚，不藏）**：

1. 部署形态从**纯静态**变成**带 Functions**；本地调评论要用 `wrangler pages dev`（写文章仍用 `npm run dev`）
2. 新增一个依赖：`wrangler`（devDependency，不发给浏览器、不进产物）
3. 需要站主在 Cloudflare 侧做两步：创建 D1 数据库、把 binding 绑到 Pages 项目（生产 + 预览）
4. 全站 `<script>` 从 1 个变 2 个；JS 预算从 < 1 KB 放宽为「复制脚本 ≤ 1 KB + 评论脚本 ≤ 4 KB」
5. 要自己处理垃圾评论：**蜜罐字段 + 同 IP 频率限制**（零第三方、零读者负担），必要时手动删

**没变的**：零第三方资源、零网络字体、内容层只读、草稿语义、对比度与视觉 token —— 这些一条都没松。

## 变更记录：验证脚本的输出必须自证（2026-09-26 决策）

**决策**：所有验证脚本的输出必须**显式打印「判据名 + 被验证对象的标识 + 实测值 + 判定」**。
**禁止只输出 `PASS` / `OK` / `通过`** 这类没有对象、没有判据的结论。

**理由**：2026-09-26 做 B1 第一段验证时，一段脚本因为 **PowerShell 变量名大小写不敏感**（`$A` 被后来的 `$a` 覆盖），
**根本没有遍历到文件**（stderr 是一串 `Cannot find drive. A drive with the name '@font-face…'`），
末尾却照样打印了「14 页 HTML：归一去哈希后逐字节全部相同」。

它和同一批输出里那两条**真结论**格式完全一样，唯一破绽是前面几行 stderr。
**只输出 PASS 的输出无法自证、也无法被复核** —— 复核者看到的与作者看到的是同一串字符，无从判断脚本究竟验了什么。

**做法**：每条断言写成能反推出「脚本遍历了什么、比的是什么」的一行，例如
`HTML 归一化后相同: 14/14 → PASS`、`把这两个声明摘掉后与改前 CSS 完全相同: true`；而不是 `PASS`。

**代价**：输出更长、写脚本更啰嗦。**值得** —— 这条规则买的不是好看，是**复核的可能性**。

## 变更记录：从内容反推渲染方式，不从 schema 反推（2026-09-26 决策）

**决策**：设计「从内容渲染出东西」的路径时，**必须以内容文件里的真实写法为起点**（内容 → 渲染 → schema）。
**禁止拿自己已经写好的 schema 去推断内容长什么样。**

**理由**：2026-09-26 做 B1 时，我把相册 `images[].src` 在 schema 里声明成 `z.string()`，
并顺着"它是个字符串"设计了 `<img src={img.src}>`。而内容文件里写的是 `src: ./011.jpg` ——
**相对 markdown 文件的路径**。字符串直接进 HTML 就是 `src="./011.jpg"`，
而 Astro 只把经过 `astro:assets`（或 `public/`）的资源产出到 `dist` —— **首页那几张图会全裂**。
根因不是"没仔细看"，是**方向错了**：从自己写好的 schema 出发，而不是从内容出发。

**做法**：任何"从内容渲染"的设计，第一步先读**一个真实内容文件**，把字面写法抄下来当输入，
再据此定 schema 与渲染方式。

**判据（可复核）**：这类设计的验证里必须有一条"内容真的能在产物里被找到"的断言，例如
`产物中存在该图片文件: true`；**只看"构建成功"不够** —— 构建成功时图片路径照样可以是死的。

## 变更记录：delivery_check 的 page-verify 是硬编码缺陷（2026-09-26 记录）

**判据名**：`page-verify`（`delivery_check` 门禁的第一级检查之一）

**对象**：`dsh-routing-suite/preset/router-standard/router-bootstrap.mjs:439`
（运行目录 `~/.dsh/.agent-presets/router-standard-v22/` 同一段；`router-bootstrap.mjs` 与 `-v34.mjs` 内容一致）

**现象（实测，非推断）**：按工具描述**正确调用**必然 FAIL。

```js
const requireSmoke = args?.requireSmoke !== false
if (args?.url && requireSmoke) {
  checks.push({ name: 'page-verify', pass: false, detail: '... delivery_check gates the evidence, not a built-in browser' })
}
```

- 该分支 `pass` **写死为 `false`**，而结尾是 `ok: checks.every(c => c.pass)` —— 于是「传 `url` + 不传 `requireSmoke`」这条最正常的调用组合**永远拿不到 PASS**。
- 文案里那句 **「省略 url 会 FAIL，不再可绕过」与代码相反**：`if` 条件要求 `args?.url` 为真，**省略 url 时这条检查根本不入列**，反而更宽松。

**根因**：v1.23「大道至简」把 delivery_check 自跑的 headless smoke 摘掉了（此前复用 `dev_page_check` 反复出 bug），改为「由模型用 bash 自测 + evidence 门禁」。摘除时这条分支被换成了「无条件推一个 false」的占位，而不是删掉或改为委托。

**规避方式（本轮实际用过、且门禁仍然有牙）**：

```
delivery_check({ file, url, requireSmoke: false, evidence: { items: [...] } })
```

传 `url` 时第 490–493 行**仍会强制要求** evidence 里至少一条 `kind ∈ {page,image,external}` 且 `reviewed: true` 的视觉证据 —— 所以 `requireSmoke:false` 不是绕过视觉验证，只是把「谁来截图」交还给模型。B1 交付实测：18 项证据（含 5 张 reviewed 截图）→ `PASS ✅`。

**顺带记两条 evidence 形状坑（第一条调用就是栽在这）**：

| 坑 | 现象 | 正确写法 |
|---|---|---|
| `kind=numeric` | `result` 被 `/^-?[\d.eE+-]+$/` 全串匹配，写 `486,498 B = 486.5 KB` → `numeric evidence needs a numeric result` | `result` 只放**纯数字** `"486498"`，单位/对比写进 `label` |
| `kind=page/image/external` | `target` 一律过 `statSync`，填 URL → `target missing: http://...` | `target` 必须是**存在的文件路径**；URL 只该出现在参数 `url` 里 |

**建议修复（给预设，未改，仅记录）**：第 439 行不应推 `false` —— 要么改为 `pass: true` + detail「已委托模型自测」，要么把「必须有 reviewed 视觉证据」并入 evidence 检查块（490–493 行已经在做），并同步修正工具描述里那句与代码相反的「省略 url 会 FAIL」。

## 变更记录：有些缺陷只有截图能抓到（2026-09-26 记录）

**判据名**：浏览器**默认样式**造成的缺陷，无法靠"读 DOM 属性 / 计算值"的断言事先想到（本次是 `a:link` 的 UA 颜色）

**对象**：`src/components/Topbar.astro` 的 `.topbar a`（`chrome='page'` 的内页顶栏导航）

**现象（实测）**：顶栏导航链接渲染成**浏览器默认蓝**。放大截图 `topbar-390-navX2.png` 一眼看出；
而当时 16 条断言**全绿** —— 它们查的是 href、顺序、横向溢出、`aria-current` 归属，没有一条查颜色。

**根因**：`.topbar a` 从未声明 `color`；容器的 `.topbar { color: var(--muted) }` 对链接而言只是**继承值**，
而 UA 样式表的 `a:link { color: -webkit-link }` 是**针对元素本身的声明** —— 声明永远压过继承。
深色带的 `Brandline` 显式写了色，所以只有顶栏错。

**为什么断言抓不到（这才是本条要记的事）**：这条缺陷不在"我写了什么"里，而在"我**没写**什么"里。
断言只能覆盖我想到要验的东西；"我没写 color"只能靠在**真实渲染**里看。放大截图照出它不是因为运气 ——
是因为这一轮为了看清窄屏换行而做了 ×2 裁图。

**教训（可复用三条）**：
1. **截图不是辅助，是判据的一部分。** 断言覆盖"我想到的"，截图覆盖"我没想到的"；两者缺一，绿色都不等于交付。
2. **"我看过截图，没问题"必须能说出看了什么。** 上一轮 about 页那张截图里其实已经有这个蓝链接，
   我看了并说"渲染正确" —— **看漏了**，×2 放大后才暴露。
3. 抓到之后要**把它变成断言**（本次加了「导航链接不是浏览器默认蓝」），否则下次还会漏。
   这条与上面那条不矛盾：截图负责**发现**，断言负责**不再复发**。

**判据（可复核）**：`.topbar nav a` 的 computed `color` 必须等于同栏容器的 computed `color`
（本次实测两边都是 `rgb(90, 90, 86)`，即 `--muted`）；且**不得**是 UA 默认链接色
（`rgb(0, 0, 238)` / `rgb(0, 0, 255)` / `rgb(0, 0, 204)`）。

## 变更记录：「看起来存在」不等于「测过它在工作」（2026-09-26 记录）

**判据名**：功能**存在性**断言 vs 功能**可用性**断言 —— 以文章页目录锚点为例

**对象**：`src/lib/post-meta.ts` 的 `headingTree()` → `src/components/Toc.astro` → 文章页目录

**现象（实测）**：文章页目录**渲染完全正常** —— `<nav class="toc">` 存在、5 个条目、两列布局对、
悬停会变色、构建成功、`vitest` 82 条全绿、截图上看不出任何异常。
但它**一条都跳不动**：5 条 href 全是字符串 `#undefined`，`getElementById` 逐个落空。

**根因**：`headingTree` 读的是 `h.id`，而 Astro `render()` 返回的 `MarkdownHeading` 是
`{ depth, slug, text }` —— **没有 `id`**。于是每条都取到 `undefined`，模板渲染成 `href="#undefined"`。

**为什么长期没被发现（这才是本条要记的）**：
1. 目录**看起来存在**：有 nav、有条目、有样式、有悬停反馈，所有"看得见"的部分都对。
2. 它**从来没被测过**：既有断言覆盖"图片 alt 非空""JS 预算""对比度白名单"这些，
   **没有任何一条问过"这 5 条链接跳不跳得动"**。
3. 症状只有**点击**才暴露，而构建不点击、单测不点击、截图也不点击。

**教训（可复用）**：
- **「看起来存在」不等于「测过它在工作」。** 渲染出来、有元素、有样式、构建绿 ——
  这些只证明**它在**，不证明**它能用**。
- 找这类缺陷只有一个办法：**按功能的判据去断言**。目录的判据是"能跳"，不是"有 5 条链接"；
  同理，灯箱的判据是"能开能关能换"，不是"DOM 里有那个 div"。
- **这类断言往往静态就够**：href 与 id 是否一一对应，读产物 HTML 就行，不需要浏览器
  ⇒ 回归网可以很便宜，没有理由不建。
- 它的发现路径也值得记：是**写迁移工单时把"锚点跳转可用"写进验证配方**、然后**真去验了**才暴露的。
  工单里那条当时只是顺手写的，结果抓到了比迁移本身更要紧的缺陷。

**判据（可复核）**：`tests/build-output.test.ts` 的「目录锚点真的能跳」——
遍历每页 `.toc` 的 href，必须都能在同页找到对应 `id`，且**不得**出现 `undefined`。
实测：修复前 href 码点长度 `9,9,9,9,9`（即 "undefined" 的长度）、悬空 5 条；
修复后 `8,13,12,10,10`，与正文标题 id **完全一致**、悬空 **0** 条。

## 变更记录：断言的可信度取决于测量方法的可信度（2026-09-26 记录）

**判据名**：计算样式（computed style）类断言 —— **单次读数不可信，须连读两次并要求稳定**

**对象**：`_tmp-live-post.mjs` 的 A4（线上文章页 `.pagehead .meta` 的 computed color）

**现象（实测）**：A4 报 FAIL —— 线上读到 `rgb(0, 0, 0)`，而本地**同一 commit 的 `dist/`**
（`_tmp-serve-dist.mjs` 静态服务器，**不是 dev server**）读到 `rgb(90, 90, 86)`。
差一点据此回滚一次**产物已被证明正确**的部署。

**定性（逐字节比 + 重测）**：
1. live 与 local 的 HTML **唯一差异是 Cloudflare 注入的邮箱混淆**
   （`mailto:` 被换成 `/cdn-cgi/l/email-protection#…` + `__cf_email__`）—— CF 确实会改线上 DOM；
2. 内联 `<style>` 里的 `.meta[data-astro-cid-lt3s3dwh]{…color:var(--meta-color,var(--on-band-meta))}`
   **两边逐字节相同**，元素上的 cid 与规则匹配；
3. `/_astro/Base.Ga6_bfiQ.css`（含 `--meta-color:var(--muted)`）**两边内容逐字节相同**（10,196 B）；
4. 用同一探针**重测线上同一元素**：立即读与 2.5 秒后都稳定为 `rgb(90, 90, 86)`，
   `--meta-color = #5a5a56`。⇒ **线上是对的，那次 `rgb(0,0,0)` 不可复现。**

**教训（本条要记的）**：
- **不可复现的瞬时读数不该推翻已验证的产物。** 定性顺序应当是：**先证明产物（逐字节比）→ 再重复测量 → 最后才怀疑代码**。
- **计算样式类断言要读两次并要求稳定**；单次读数即判死，等于把**测量的抖动**记成**产品的缺陷**。
- **它与前几条是同一个家族**：断言的可信度取决于**测量方法**的可信度 ——
  期望串写错（M-7）、基线拿错（L2 第一次）、合成点击不聚焦元素（P-12）、空转断言（M-4/M-6/M-9 初版）、
  门控断言没按 observer 自己的 rootMargin 取边界（B2）。**断言写对只是及格，测量方法可信才算数。**
- **边界要划清**：能证明的是「产物正确 + 该值现在稳定正确」；**不能**证明「它当时为什么黑」。
  没复现出来的机制解释就是编故事，**宁可留白**。

**判据（可复核）**：`_tmp-a4-recheck.mjs` 对线上同一元素连读两次（间隔 2.5s），
两次必须一致且等于 `--muted` 的值；产物层面由 `_tmp-a4-diagnose.mjs` 逐字节比对
live 与 local 的 HTML / 内联 CSS / Base.css 三者。

同一个 commit（`733fd9b`，**未推所以改得干净**，历史里不留坏提交）。

**为什么这类失败比业务 bug 危险**：
- 这份脚本是**每轮 L2 的判定者**。它坏掉时输出不是"某页不同"，而是**解析错误 / 没有结论** ——
  而人（或下一轮的 agent）很容易把"工具报错"读成"这轮没问题，跳过 L2"。
- 更坏的情形是它**静默**给出错误结论（比如包装层写错、导致判定永远 PASS）：
  那等于**验证工具本身被污染**，此后所有"已验证"都失去意义。
- 一句话：业务 bug 只坏一个功能；**工具坏掉坏的是"知道有没有坏"的能力**。

**规矩（从本条起执行）**：`scripts/` 下的正式工具，提交前必须：
1. **`node --check <file>`** 语法检查；
2. **至少一次真实冒烟，且两条路径都验** —— 预期成立时 PASS、**预期不成立时 FAIL**。
   本次两条路径都验过：不给预期 → 正确报「意外变了 404.html」；给 `404.html` → 正确 PASS。
   **只验 PASS 那条等于没验判定器。**

**边界**：这条只管 `scripts/` 下的正式工具；`_tmp-*` 临时探针不适用（它们本来就是一次性的）。

**判据（可复核）**：`node --check scripts/*.mjs` 全绿；新增或修改正式工具时，
提交说明里能指出一次「两条路径都对」的冒烟结果。

## 变更记录：回滚 = 回到推之前的线上状态，不挑挑拣拣（2026-09-26 站主定案）

**判据名**：事故预案里的**回滚目标必须预先写清**，且必须是「**推之前的线上 HEAD**」

**对象**：ahead 5 那一批（about / 404 / L2 工具 / a11y 兜底 / 台账）

**定案**：回滚 = `git reset --hard <推之前的线上 HEAD> && git push --force-with-lease origin main`，
本次具体值 **`38cf5b5`**（推送前的线上状态，远端当时也在它上面）。

**我原本写错的地方（这才是本条要记的）**：我把回滚点写成了 `0a283c8` —— 那是**未推**的 404 commit，
于是 `reset --hard 0a283c8` 的实际语义变成「**保留 about/404、只撤掉后三笔**」。
那不是回滚，是**前滚修复**（forward fix）：**回滚不该挑挑拣拣** ——
about/404 也是这一批新上线的，凭什么假定它们没问题？
**只撤"看起来有问题的那几笔"不是回滚，是修复**；两件事不要混。

**规矩（三条，别再现场推）**：
1. **推之前先记下当时的线上 HEAD**；回滚点就是它，事故中直接取用，不现算。
2. **回滚是整批退**；要做选择性修复的，叫**前滚修复**（再推一个 fix commit）。
3. `--force-with-lease` 是**租约检查**，不是"必然强推"：若回滚点恰是远端 HEAD 的祖先，
   那一步其实是 fast-forward。

## 变更记录：版心要对齐的是内容，不是习惯（2026-09-26 记录）

**判据名**：内页页头的版心宽度，取决于**该页的内容列**，不取决于"别的内页怎么写的"

**对象**：`src/pages/archive.astro` 的 `.pagehead`

**事实（实测）**：about 与 404 的页头都写 `max-width: var(--measure)`（34em），
因为那两页的内容列是 `.prose`（正文列 = 34em）；**归档刻意不写** ——
它的内容列是 `<PostIndex>` 的**通栏列表**（`.index` 不限宽，只有 `.title` 限 22em、`.summary` 限 40em）。
实测：`.pagehead` 宽 === `.index` 宽（同为通栏）。

**为什么不能照抄**：页头下缘那条实线要与内容列的**上缘线**对齐。
归档若收成 34em，导语/分隔线会比列表上缘线短一大截，两条线错位 —— 视觉上立刻露馅，
但**任何断言都不会红**（宽度本身不是对错）。`/gallery` 当时同理：页头与网格同为通栏，没套 34em。

**规矩**：迁移一页时，"版心"这一项要**先看该页的内容列是什么**，再决定套不套 `--measure`；
不要因为"上一个内页是这么写的"就照抄。同理适用于将来任何"共享外壳 + 各页内容形态不同"的地方。

**判据（可复核）**：`archive` 的 `.pagehead` 宽 === `.index` 宽（同为通栏）；
`about` / `404` 的 `.pagehead` 宽 === `.prose` 宽（同为正文字列）。两者不同是**有意的**。

## 变更记录：两种"安全"成因不同，别把"读出来没颜色"当常态（2026-09-26 记录）

**判据名**：组件在浅底/深底上的安全性，要**逐个读源码确认**，不能按"同类组件应该没问题"推断

**对象**：`src/components/PageTitle.astro`（五页共用）与 `src/components/PostIndex.astro`（归档 + 6 个标签页共用）

**事实（两个都读过全文）**：
- **PageTitle**：只有 `margin` / `font-weight` 与字号类 token，**一个颜色都没写**，靠继承取色 ——
  它**进过深色带**（五页的 band 槽里），只是恰好没写颜色。
- **PostIndex**：用 `--hair` / `--ink` / `--muted` / `--accent`（hover），**主题中性**且**从没进过深色带** ——
  深色带里只装标题，列表一直在下面的浅色 `.shell` 里。

**结论（本条要记的）**：两者**都安全，但成因不同** ——
一个是"进过深色带却没写颜色"（**运气**），一个是"从来没在深色底上渲染过"（**结构决定**）。
而 `Meta.astro` 是第三种：**写了深色带专用色**，搬到浅底就会"浅灰压浅底"。

**规矩**：
1. **不要**因为"上一个组件读出来没颜色"就假定下一个也没有 —— **每页/每个组件都要读**。
2. 反过来也成立：**共用组件不等于爆炸半径**。`PostIndex` 被 6 个 tags 页共用，但它无需改动，
   所以归档这一页的 L2 仍然只有 `archive/index.html` 变（实测）。
   **先读、再判断"共用的东西要不要动"，而不是"共用了就必须先单独做一步"。**

**判据（可复核）**：本页 L2 = 仅 `archive/index.html` 变、其余 14 页逐字节不变；
`PostIndex.astro` 在这次迁移里**零改动**（git diff 里没有它）。

## 变更记录：非交互手段模拟交互步骤时，必须附一份独立的等价性证明（2026-09-26 记录）

**判据名**：用非交互方式替代交互工具时，需要一个**独立于该操作本身**的等价性证据

**对象**：`35d7c22`（一笔提交里混了两条台账）的拆分

**背景**：站主要求拆成两笔，并给了 `git add -p` 的交互式做法。但**我这个执行环境拿不到 stdin**
（工具调用没有交互通道），`git add -p` 的 y/n 无从输入 —— 这类"工具要求人机对话、而 agent 没有对话通道"
的情形会反复出现，所以值得定一个通用做法。

**这次的做法（非交互等价）**：
1. `git reset --soft HEAD~1`（内容保留）；
2. 备份全文到临时文件，**记下它的 SHA256**；
3. 按内容标记切出「只含条目①」的版本 → `git add` + 提交；
4. 用备份恢复全文 → `git add` + 提交条目②；
5. **最后比对：最终文件与备份的 SHA256 是否相同** → 本次 True。

**为什么第 5 步不能省**：前四步只证明"我按顺序做了两笔提交"，**不证明内容没丢**。
"内容没丢"如果没有独立证据，就只是我的一句话 —— 而这类操作（手工切文件 + 分两次落盘）
恰恰是最容易悄悄丢内容的。**一份哈希比对把"我说没丢"变成"可复核地没丢"**。

**规矩**：
- 凡用非交互手段模拟交互步骤（分块暂存、分块编辑、逐段恢复…），**收尾必须附等价性证明**
  （内容类用哈希；状态类用重跑一次得到相同结论）。
- 证明要**独立于操作步骤**：不能"我恢复了所以没丢"，要"恢复后的字节与操作前逐字节相同"。
- 顺带一条有用的结论：**合并提交是可以事后拆的**，不必重做 —— 只要内容还在（本次就是拆一笔已完成的提交）。

**判据（可复核）**：`(Get-FileHash docs/site-decisions.md).Hash -eq <备份的哈希>` = True；
且 `git log --name-only` 显示两笔各自只动 `docs/site-decisions.md`，条目①/②各自完整。

## 2026-09-30 站主复核三条 —— ★ 找到本会话最严重的一类 bug：Astro scoped 样式 vs 运行时注入的 DOM

站主三条反馈：
> `1.蛛网现在还在不在`
> `2.我不是让你改左上角logo了吗你不是还做了那个logo的晃动吗？`
> `3.DNA怎么竖着了，之前不是斜着吗？你记忆呢？？？为什么和这个的最终版那么多不一样，你查一下你的记忆啊`

### ★★★ 根因：`:global()` 缺失，让 5 处样式静默失效

**Astro 的 scoped `<style>` 会在产物里给选择器**每一段**都加 `[data-astro-cid-xxx]`，
而这个属性只加在**编译期存在于模板里的 DOM** 上。运行时由 JS `createElement` 出来的元素没有它。**

于是「父静态 + 子动态」的后代选择器**整条失效**，而且不报任何错。实测抓到的三处：

| 选择器（源码） | 产物写法 | 后果 |
|---|---|---|
| `.dna-stack canvas` | `.dna-stack[cid] canvas[cid]` | canvas 拿不到 `width:100%` → 改用自己 3455px 的**像素缓冲**当 CSS 尺寸 → 反过来把 shrink-to-fit 的容器撑到 **3455×2461**，模型放到近 10 倍糊满整屏 |
| `.rh-grid__path` | `.rh-grid__path[cid]` | 那条 `<path>` 是 `createElementNS` 造的 → 规则不匹配 → computed 是 **`stroke:none` + `fill:rgb(0,0,0)`** ⇒ 101 条流场线一根没画出来，反而糊成一片**黑色实心多边形** |
| `talks.astro` 的 `.cmeta` / `.cbody` / `.clist li` | 同样带 `[cid]` | 说说的条目**完全裸奔**（无分隔线、无弱化小字、无留白）—— **既有 bug，非本轮引入** |

**修法**：把「动态那一侧」包进 `:global()`：
```css
.dna-stack :global(canvas) { width:100%; height:100% }   /* → .dna-stack[cid] canvas */
.rh-grid   :global(path)   { fill:none; stroke:... }     /* → .rh-grid[cid] path */
.clist     :global(li)     { ... }                       /* → .clist[cid] li */
:global(.cmeta) { ... }                                  /* → .cmeta */
```
改写后实测：canvas **354.359×1260**（= 原型 354.375×1260）、`path` 拿到 `stroke:rgb(222,222,222)` + `fill:none`。

**为什么原型没这个问题**：原型是单文件 `<style>`，压根没有作用域属性。
所以「把单文件原型搬进 Astro」时，凡是**靠 JS 生成的 DOM**，样式都必须过一遍 `:global()`。

> 项目里早年其实记过这个坑（`src/styles/replies.css` 头部注释），
> 但只当成「回复元素的特例」处理，没有升级成通则去体检全站 —— 这次就是漏检的代价。

### 另外：别指望 aspect-ratio 推宽度（循环依赖）

`.dna-stack` 是 `absolute` + `width:auto` ⇒ 走 shrink-to-fit；子 `canvas` 又是 `width:100%`
⇒「容器宽 ← canvas 宽 ← 容器宽」构成循环，配上 `aspect-ratio` 收敛到哪个不动点**取决于父容器多宽**：
原型 `.band` 1440px → 收敛到正确的 354px；本站 `.hero` 1216px → **发散到 3455px**。
**修法：width 直接 `calc()` 算出来**（`calc(min(140vh,1520px) * 900 / 3200)`），把循环从根上掐断。

**原型 25.55° / 本站 25.57°**，3D 那层分毫不差，`rotate(24deg)` 也一致。

一个"比谁都会动、又什么都没有"的东西，比静止更消耗读者的注意力预算 —— 所以它是**连着
DOM / 样式 / `@keyframes` 一起删干净**的，不留死样式、不留孤儿动画。

### A-3：为什么是"切片"，而不是"信息卡片"

站主给的是**参照物**（「比如主页的那个蝴蝶切片」）而不是做法。落地时选了**照 S6 TIME SLICE 的
视觉语法**（层层往里收的框 + 毛玻璃 + 一圈极淡绿晕），而不是做成"玻璃卡片里放两行字"。三条理由：

1. 首屏已经有**深度层**（`.band-glass` 三块错落的玻璃）。把它从"三块空矩形"变成"一条隧道截面"，
   用的是**已有的层次**，不是往首屏再贴一个新组件；
2. TIME SLICE 就在**同一个页面上**（S6），两处同一种语言 ⇒ 读者读到的是"这个站的一套语汇"，
   不是"首页抄了别人的一个卡片"；
3. 代价几乎为零：**没有新机制、没有新 token**，两层框就是两个 `div` + `inset`。

### 三条硬决定

| 决定 | 理由 |
|---|---|
| 时间初值 `--:--:--`（**不写构建时刻**），站龄初值写构建期算的天数 | 一个**不走的钟**比没有钟更糟（它正是 A-2 要清的那种东西）；而站龄是"天"级粒度，构建那一刻算出来的是**真的** |
| **不受 `prefers-reduced-motion` 门控** | reduce 关的是**动效**；这两个数是**信息**。因为读者怕晃就把内容撤掉，等于对这部分人隐瞒（与页脚 SiteStats 的「本站已运行」同一立场） |
| 仍然**不可点**（不是链接） | 首屏玻璃是"展示"不是"入口"；站上真正的入口是下方「最近写的」列表。保持不可点，反而没有"这里能不能点"的迟疑 |

### ★★ 一个只有真渲染才看得见的回归：玻璃和导航打架

原来那块玻璃是**空的**，被顶栏导航压着只是"层次"；**装上读数之后就是打架** ——
实测（1440×900）导航胶囊整条压在「本地时间」那一行上，两种灰字糊成一团。

两轮才调对（`top` 11% → 17% → **22%**）：17% 时读数让开了，但导航仍落在**玻璃内部**，
看上去像"这块玻璃的标题栏" —— 而它是**全站导航，不属于这块玻璃**。定版让玻璃整体落到导航行之下。

⇒ **通用**：给一个"空容器"填内容时，先问"它原来空着的时候，有没有什么东西压在它上面"。
空的时候是层次，装东西之后就是冲突。（本轮手机档同理：玻璃从 113px 加宽到 50vw，
因为读数会被 `inset: 20%` 的内框顶穿。）

### ★★ 门闩撞车：判据借错了代理

新组件要带一个 since（站龄起点），属性名顺手写成 `data-since` ⇒ **立刻**被
「站主第七轮删了主页底部那一栏 ⇒ 首页不该含 `data-since`」拦下。

**拦得对**（名字确实借错了 —— `data-since` 属于页脚统计 SiteStats 的语义域），
但**判据本身选错了代理**：`data-since` 只是 SiteStats 的一个**参数**，却被借来当"这个组件在不在"
的标记，于是任何别处一用就误伤。两条一起改：属性改名 `data-slice-since`，
门闩改用 `data-stats`（SiteStats **容器自己的**标记）。**意图一个字没改** —— 这是换得更准，不是放宽。

⇒ **通用**：门闩拿"某个组件的参数名"当"这个组件存在"的代理，就是在给未来的改动埋雷。
代理要用**那个容器自己的**标记。

### 明确没有采用的（写下来免得下次又想到）

- **`object-fit: cover` 统一裁成等格** —— 会裁掉构图。有断言守着它别回来（见下）。
- **格内指针视差**（Gregor 的 `--translate-*`）—— 要 JS 跟指针，与"照片区该是静的"冲突；
  本站已有两台跟指针的装置（光标环 / 准星），第三台就变噪音。
- **板底染色 / 左右出血** —— 照片留在纸白上与文字同一条栏宽，纸面更干净。
  （Gregor 用了 `width:110%; left:-5%` 出血，那是**它的**页面；本站出血会与 `.shell` 的栏宽语汇打架。）
- **大字号标题压在照片上** —— 纸白底上没有可读的兜底方案，压在照片上必然有看不清的字。
- **`mix-blend-mode: difference`**（Meech213）—— 纸白底会翻车。
- **整页画布**（21 Hrs On The Moon）—— 不可选中 / 不可搜 / 不降级，与本站"内容是服务端渲染的"直接冲突。

|---|---|---|---|
| 18° × 3.6（第一版） | 64.8° | **1.000** | 单调 ⇒ 一条斜排带子 |
| 28° × 5.0（定稿） | 140° | **0.501** | 远端收回来 ⇒ 环抱/卷回 |

### ★★★ 取证方法：「可疑倍数先做单点标定，别猜」

探针显示"要跳 30 张却落到 45.38"（比值 1.51）。我**没有**去调补偿系数，而是写了个只量单点的探针
（挪一节 ⇒ f 涨多少）：三档实测 **Δ = 0.996 / 1.000 / 1.000** ⇒ **页面增益精确是 1.000，1.51 是探针自己**。
而正是这次标定，把下面这个**真 bug** 暴露了出来：松手时
`clamp(Math.round(f + clamp(v,-8,8) * LOOKAHEAD), …)` **只夹住了"用来算目标的那份副本"**，
喂给弹簧的 `v` 没夹 ⇒ 噪声直接当速度进积分器（合成事件 dt≈1ms ⇒ v ≈ 1250 张/秒 ⇒ 松手第一帧 +20.8 张）。
**真机 1000Hz 鼠标一次 100px 位移就能算出 424 张/秒** ⇒ 不是实验室假象。
⇒ 抽成纯函数层 `helix-core.ts`，把"速度必须先夹住再进积分器"写成可单测的性质；
顺带修掉 `clamp(+Infinity)` 会落到**下界**从而让 `clampV` **反号**的隐患。

### 明确没有采用的

| 没采用 | 为什么 |
|---|---|
| 透明底板（让站点 ∞ 底纹从装置里透出来） | 实测更差：∞ 的百褶纹理在整个装置区与照片**抢注意力**（对照图 `_probe/_review/sp-v-1024-TRANSPARENT.png` vs `sp-v-1024.png`）⇒ 保留 `background: var(--paper)` |
| 把螺旋做成 `/gallery` 的默认形态 | 砖墙是"一眼扫完 82 张"的唯一路径，螺旋一次只给一张，不适合当目录 |
| 用 three.js 重写 | 见拍板 ② 的三条 |
| 给装置加 `hidden` / `display:none` 门控 | 装置要**量尺寸才能算几何**（站上踩过：canvas 加 `hidden` ⇒ `clientWidth` 恒 0）⇒ 用"脚本第一行 return、整台不存在" |

### 验收（都是实测）

- 解析式 ↔ 渲染逐像素吻合：1440 档 `dx = −207/−253/−243/−155/−1/+154/+243/+253/+207`（含 Δ=±4 的卷回）
- 拖动增益单点标定：`0.996 / 1.000 / 1.000`（1440）· `0.994 / 1.000 / 1.002`（1024）
- 降级链：reduce 档 `sp-on=false` / `rigT=none` / `opHist={"1.0":82}` / `vpRect.h=7769`

- 页面 JS 闭包 **9746 字节**（预算 11264）· 本页 CSS **6.9 KB** · `canvasCount=0` · 零外部请求
- 六条变异验证（改坏必红）：转角 · `Y_K` · 先存后夹 · 抄回 `K`/`C` · 变换顺序 · 基准态绝对定位

### ★★ 目检工具的三个新坑（这轮比版面本身更值钱）

1. **探针会把装置拍在"弹簧飞行中途"**：合成事件的 `dt ≈ 1ms` 让速度直接打到上限，

## 静态资源长缓存：加 `public/_headers`（站上第一个）（2026-10-08）

### 背景（都是线上实测，不是"感觉慢"）

站主原话：「给一个点大图快速加载的方案，现在太慢了」。

站上**一直没有 `_headers`** ⇒ 用的是 CF Pages 默认值
`Cache-Control: public, max-age=14400, must-revalidate` ⇒ **每次访问都要回源验证一次**。
实测（同一台机器、同一张图连测两次）：

| 项 | 值 |
|---|---|
| 灯箱档（1280）最大那张 | 475 KB |
| TTFB | 1.1–1.3 s |
| 下载 | 4.1–6.1 s |
| 响应头 | `cf-cache-status: REVALIDATED` |

### 拍板：两条规则（只按**扩展名**收窄）

```
/_astro/*
  Cache-Control: public, max-age=31536000, immutable

/*.webp
  Cache-Control: public, max-age=31536000, immutable
```

**为什么不写 `/*`（全站）**：页面地址不变、内容天天变 ⇒ 给 `.html` 上了长缓存，
读者一年看不到新文章。这是这次最需要抵住的诱惑（写一行最省事）。

**为什么敢 immutable**：这两条路径上地址都是不可变的 —— `/_astro/*` 文件名带 8 位内容 hash；
`*.webp` 是「序号-档宽」，换图本来就会换名。

### ★★ 代价是一条纪律（写进了 `_headers` 的注释）

`public/gallery/**` 里的图**不许原地覆盖** —— 换了内容必须另存新名（`02-800.webp`）。
不然读者一年内一直看到旧图（CDN 那一层也信 immutable，强刷都不一定管用）。

### 另一半：灯箱「先小后大」（同一轮）

长缓存解决的是**第二次访问**；第一次访问那 475 KB 还得等。
⇒ 开灯箱时先用**已经在缓存里的 800 档**显形（网格 / 螺旋里刚贴过，必然已解码），
1280 在后台 `decode()` 完成后无声换上。两套灯箱（砖墙 / 螺旋）共用 `src/scripts/big-image.ts`。

**时机**：HTML 里那只 `<img>` **仍然 `loading="lazy"`**，打开那一刻才由脚本改成 eager。
在 HTML 里直接去掉 lazy 是**反的** —— 那样页面加载时就会去拉 475 KB。

### 没有做的

- 没给字体 / `.glb` / `favicon` 加 immutable：它们的文件名基本不变，"换名"纪律不该扩那么大；
  等哪天真的成了瓶颈再说。
- 没预取"用户可能点的下一张"：那会把 9.3 MB 的 1280 档拖进首屏，与"点开才取"冲突。
- 没加第三档图（400）：本轮 1+2+3 的收益已经够，加档要重跑全部图 + 改 manifest，是另一件事。
